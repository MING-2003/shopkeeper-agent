## 一、方案选型：不用 uv，改用 conda

项目 README 推荐 `uv` 管理依赖，但本机选择 conda。两者对应关系：

| uv 命令 | conda 替代 |
| --- | --- |
| `uv sync` | `conda create` + `pip install -e .` |
| `uv run xxx` | 激活环境后直接 `xxx` |
| `uv run hf download` | `hf download` |

关键认知：`pyproject.toml` 才是依赖清单（17 个直接依赖 + 最低版本范围），`uv.lock` 是 uv 专用版本锁定文件，pip/conda 都不认识，直接无视。

## 二、创建 conda 环境

本机 conda 只有 defaults 频道，为遵守国内镜像原则，创建时显式指定清华 conda-forge 镜像（不改全局配置）：

```bash
conda create -n shopkeeper python=3.14 -c https://mirrors.tuna.tsinghua.edu.cn/anaconda/cloud/conda-forge --override-channels --yes
```

结果：环境装在 `C:\Users\GU\.conda\envs\shopkeeper`，Python 3.14.7，满足项目 `requires-python >= 3.14`。

## 三、安装后端依赖

配置清华 pip 源后执行 `pip install -e .`，**报错**：

```text
error: Multiple top-level packages discovered in a flat-layout:
['app', 'conf', 'docker', 'prompts', 'frontend'].
```

**根因**：`pyproject.toml` 没有 `[build-system]` 配置段。uv 装依赖时不构建项目本身（所以原作者没遇到），而 `pip install -e .` 必须构建项目，setuptools 自动发现时看到 5 个顶层目录就拒绝继续。

**解决**：在 `pyproject.toml` 顶部补充构建配置，显式只打包 `app`：

```toml
[build-system]
requires = ["setuptools>=61"]
build-backend = "setuptools.build_meta"

[tool.setuptools.packages.find]
include = ["app*"]
```

之后安装顺利完成。最终 `pip list` 核对：17 个直接依赖全部满足版本要求，`shopkeeper-agent 0.1.0` 以可编辑模式挂载（`Editable project location` 列可见），全部核心包 import 验证通过。之前担心的 C 扩展包 `asyncmy`（0.2.15）直接有 wheel，没遇到编译问题。

**经验**：pip 和 uv 行为差异是 conda 方案的第一个坑；装完用 `pip list` 对照 `pyproject.toml` 逐项核对版本，是排查依赖问题的基本功。

## 四、配置 LLM API Key

复制 `.env.example` 为 `.env`，写入 `LLM_API_KEY`。

当时即注意到 key 格式可疑（后半段像一段 base64 签名数据），但没有深究——这个坑在最后联调时才爆发（见第十一节）。

**教训**：配置 API Key 时当场核对格式（硅基流动/百炼的 key 都是 `sk-` 开头的纯字母数字串），并确认 key 属于哪个平台，能省掉后面的排障时间。

## 五、下载 Embedding 模型（坑最多的环节）

模型 `BAAI/bge-large-zh-v1.5`（约 1.30GB），必须下载到项目指定位置：

```text
docker/embedding/bge-large-zh-v1.5
```

原因：`docker-compose.yaml` 把这个目录挂载为 TEI 容器内的 `/models/bge-large-zh-v1.5`，位置错了容器起不来。这个目录下载后不能移、不能删。

### 坑 1：Xet 协议导致 401

用 `hf-mirror.com` 镜像下载时，`hf` CLI 默认走 Xet 新协议下载大文件，Xet 会绕过镜像直连 `cas-server.xethub.hf.co`，该服务对匿名请求返回：

```text
RuntimeError: File reconstruction error: CAS Client Error: HTTP status client error (401 Unauthorized)
```

**解决**：禁用 Xet，回退到普通 HTTP 下载（才会真正走镜像）：

```bash
set HF_ENDPOINT=https://hf-mirror.com
set HF_HUB_DISABLE_XET=1
hf download BAAI/bge-large-zh-v1.5 --local-dir docker/embedding/bge-large-zh-v1.5
```

### 坑 2：下载到 90% 时 MemoryError

1.17GB / 1.30GB 时进程崩溃：

```text
File "httpx\_decoders.py", line 241, in decode
    self._buffer.write(content)
MemoryError
```

**根因**：httpx 下载大文件的内存开销叠加系统内存紧张（Docker Desktop/WSL 同时在运行）。后面的 `lost sys.stderr`、tqdm `__del__` 报错都是崩溃后的噪音，不用管。

**解决**：关闭 Docker Desktop 等大内存程序后重试。重跑时命中断点续传（已下载的 11 个小文件不重下，只补最后的大文件），中途出现几次 `The read operation timed out` 但 CLI 自动恢复续传，最终 `12/12` 文件、`1.30GB` 重建完成。实际落盘权重文件为 `pytorch_model.bin`（该仓库提供的格式，TEI 支持加载）。

**备选方案**（本次未用上但值得记录）：如果 hf CLI 反复内存崩溃，直接用 Windows 自带 curl 下载单个大文件，内存占用固定小、支持断点续传：

```bash
curl -L -C - -o docker/embedding/bge-large-zh-v1.5/model.safetensors https://hf-mirror.com/BAAI/bge-large-zh-v1.5/resolve/main/model.safetensors
```

**教训**：排查"下载失败"先分清是网络问题、协议问题还是本机资源问题；huggingface 下载家族的问题近两年多半出在 Xet 协议上。

## 六、安装 Docker Desktop

### 坑 1：误以为装过 Docker

用户记忆中"装过 Docker"，实际排查发现：

- `docker` 命令不存在，`C:\Program Files\Docker` 不存在
- 注册表已安装程序列表（HKLM/HKCU）和开始菜单均无 Docker
- Everything 搜索到的大量"docker"文件都是黑马教程课件和各项目源码里的 docker 配置目录，不是软件本体

**结论**：Docker 之前装在虚拟机里，宿主机从未安装。虚拟机里的 Docker 对本项目不可用（compose 的模型挂载是 Windows 相对路径、端口转发链路长），必须装 Windows 版 Docker Desktop。

### 坑 2：启动报 "Virtualization support not detected"

Docker Desktop 装完启动报错，左下角 "Engine stopped"。

**排查过程**：

1. `systeminfo` 显示 "A hypervisor has been detected"——CPU 虚拟化硬件本身是开着的
2. `wsl --status` 显示"未安装适用于 Linux 的 Windows 子系统"——真相大白：Docker Desktop 的 WSL2 后端依赖 WSL，报错文案有误导性

**解决**（需管理员权限）：

```bash
wsl --install --no-distribution
```

然后**重启电脑**（Windows 功能必须重启生效）。重启后 Docker Desktop 正常进入界面。

### 坑 3：UI 显示 Engine running 但命令连不上

`docker ps` 报 `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`，用 PowerShell 查命名管道发现 docker 管道完全不存在，`tasklist` 也查不到 Docker 进程——**Docker Desktop 只是开着过，后来退出了**。

**解决**：重新启动 Docker Desktop，等左下角绿色 "Engine running"。

**最终验证标准**（三层，缺一不可）：

1. Docker Desktop 界面左下角绿色 Engine running
2. `docker --version`、`docker compose version` 有输出
3. `docker ps` 不报错（守护进程真正在工作）

### 镜像加速

拉镜像前配置国内加速（Settings → Docker Engine 的 JSON 中加）：

```json
"registry-mirrors": ["https://docker.m.daocloud.io", "https://docker.1ms.run"]
```

实测 `hello-world` 拉取成功（Docker Hub 链路通）；另外配合 Clash 代理打通了 `ghcr.io`（本项目 TEI 镜像来源）。

## 七、启动 5 个基础容器

```bash
docker compose -f docker/docker-compose.yaml up -d
```

镜像全部拉取/构建成功（注意 elasticsearch 服务是本地 `build: ./elasticsearch` 构建的，比纯拉取慢），4 个容器起来了，**唯独 mysql 报错**：

```text
Error response from daemon: ports are not available: exposing port TCP 0.0.0.0:3306 ... bind: Only one usage of each socket address
```

**排查过程**（有波折）：

1. `sc query` 找到本机装有名为 `MySQL` 的 Windows 服务
2. 尝试 `net stop MySQL` 却报"没有启动该服务"（错误 3521）
3. 怀疑是 Hyper-V 保留端口区间，用 `netsh interface ipv4 show excludedportrange protocol=tcp` 检查——3306 不在保留范围内，排除
4. 再次 `netstat` + `sc query MySQL`：3306 上无任何监听者，MySQL 服务状态 STOPPED（且带 1067 进程崩溃退出码）

**结论**：是本机 MySQL 服务当时正在运行/崩溃重启过程中的**瞬时冲突**，当前 3306 完全空闲。

**解决**：直接重跑 `docker compose -f docker/docker-compose.yaml up -d`，5 个容器全部 Up。另建议把本机 MySQL 服务改成手动启动，防止重启电脑后它自动起来再抢 3306：

```bash
sc config MySQL start= demand
```

**教训**：端口冲突报错只代表"报错那一刻"有人占着端口，排查要看重当下实时的 `netstat` 结果；服务"存在"不等于"正在运行"。

## 八、构建元数据知识库

```bash
python -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml
```

**报错**：

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for HuggingFaceEndpointEmbeddings
  Value error, `model` must be a HuggingFace repo ID, not a URL.
```

**根因**：项目代码有意把本地 TEI 服务 URL（`http://localhost:8081`）传给 `HuggingFaceEndpointEmbeddings(model=...)`。`uv.lock` 锁定的版本是 `langchain-huggingface 1.2.1`（允许传 URL），而 pip 装到了最新的 1.2.2——新版给这个类加了校验，只允许 HF 仓库 ID，拒绝 URL。

**解决**：降级到锁定版本（不改任何代码）：

```bash
pip install "langchain-huggingface==1.2.1"
```

**结果**：构建成功，5 项全部完成——表/字段入 MySQL 元数据库、字段向量索引（Qdrant）、字段取值全文索引（ES）、指标入库、指标向量索引。日志中出现 Qdrant 客户端(1.19.1)与服务端(1.16.3)版本差异 UserWarning，不影响运行，暂不处理。

**教训**：这是 pip 与 uv.lock 版本差异的第二个坑。凡是"传 URL/传路径被新版校验拒绝"这类报错，先去 `uv.lock` 查项目锁定版本，`pip install 包名==锁定版本` 降级即可。

## 十一、前后端联调：LLM 401（最后一个坑）

前端发起提问"统计华北地区的销售总额"，链路走到一半报错：

```text
app.agent.nodes.extract_keywords ... 抽取关键词成功: ['统计', '第一季度', ...]   ← 这步成功了
app.agent.nodes.recall_column - 召回字段信息 failed:
Error code: 401 - {'code': 30014, 'message': 'Token is invalid.'}
```

**排查关键**：确认"抽取关键词"节点是纯本地 jieba 分词（`jieba.analyse.extract_tags`），不联网，它的成功不能证明 key 有效；"召回字段信息"节点（`recall_column.py` 第 44-46 行，`prompt | llm | output_parser`）才是第一个真正调 LLM 的节点。错误码 30014 是**硅基流动**的"令牌无效"。

**根因**：用户的 API Key 实际是**阿里云百炼**的，而项目默认 `base_url` 指向硅基流动——拿 A 平台的 key 调 B 平台的接口，必然 401。（也解释了第四节 key 格式的疑惑：百炼 key 格式与硅基流动不同。）

**解决**：修改 `conf/app_config.yaml` 的 llm 段（并按要求添加注释说明原因）：

```yaml
llm:
  model_name: qwen-plus
  api_key: ${oc.env:LLM_API_KEY}
  base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
```

要点：百炼提供 OpenAI 兼容端点，所以只需改 `base_url` + `model_name`，代码零改动；`.env` 里的 key 保持不变；改完**重启后端**（配置启动时读取）再测试。

**教训**：`401 Token is invalid` 除了"key 错"还有一种常见情况是"key 和平台不匹配"。排障时先确认 key 的归属平台，再核对配置里的 `base_url`。

## 十三、踩坑经验总结

1. **pip 与 uv 的行为差异**是 conda 方案两大坑的来源：需要补 `[build-system]`；依赖版本要对照 `uv.lock` 锁定值降级
2. **huggingface 下载**：国内镜像必须禁用 Xet（`HF_HUB_DISABLE_XET=1`）；大文件下载注意内存余量；curl 直连 resolve 地址是兜底方案
3. **Docker Desktop 报错文案不可全信**："Virtualization support not detected" 实际是缺 WSL；UI 状态与真实进程状态要交叉验证（`tasklist` + `docker ps`）
4. **端口冲突**先看实时 `netstat`，"服务存在"≠"端口被占"；Windows 保留端口用 `netsh interface ipv4 show excludedportrange` 排查
5. **LLM 401** 先核对 key 归属平台与 `base_url` 是否一致，再怀疑 key 本身
6. **排查顺序**：先读报错全文 → 定位第一现场（哪个组件/节点）→ 查该组件的版本与配置 → 最小化复现验证假设

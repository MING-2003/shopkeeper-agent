# 新增中间件接入指南

> 本文档总结向项目接入一个新的外部中间件（数据库、缓存、消息队列、HTTP 服务等）的标准流程。
> 以 2026-11-12 接入 Redis（分层缓存，见 `improvement-implementation-plan.md` P2-7）为实际范例。

---

## 一、适用判断：什么该走这套流程

**要持有网络连接 / 句柄的，走这套流程；纯配置或纯逻辑的，不用。**

| 情况 | 是否走流程 | 例子 |
| --- | --- | --- |
| 需要 TCP/HTTP 长连接的中间件 | 走 | Redis、Qdrant、ES、MySQL、TEI rerank |
| 第三方 SDK 的回调/钩子 | 不走（集成点在业务参数里） | Langfuse：在 `astream` 的 config 传 callback |
| 纯本地规则，无外部依赖 | 不走 | 图表类型推荐 |
| 只读一个环境变量 | 不走 | 直接读 `.env` 即可 |

---

## 二、固定骨架：六步接线

**配置对象 → client manager 单例 → lifespan 生命周期 → 依赖注入 → 业务消费**，
这套骨架的价值是可预期性：任何人不看实现也知道连接在哪建、在哪释放、从哪注入。

以 Redis 为例（括号内为对应文件）：

| 步骤 | 做什么 | 本范例的落点 |
| --- | --- | --- |
| 1. compose 加服务 | Docker 部署的基础设施加 service 块；宿主机端口冲突时映射到备用端口并**注释说明** | `docker/docker-compose.yaml`（`6380:6379`） |
| 2. 加配置 | `app_config.yaml` 加配置段 + `app_config.py` 加 dataclass 挂到 `AppConfig` | `redis: {host, port}`；端口与 compose 映射保持一致 |
| 3. 建 client manager | 新建 `app/clients/xxx_client_manager.py`：`init()/close()` + 模块级单例 | `app/clients/redis_client_manager.py`（新增） |
| 4. lifespan 注册 | 启动阶段 `init()`，关闭阶段 `await close()`，与现有 manager 并列 | `app/api/lifespan.py` |
| 5. 依赖注入 | `app/api/dependencies.py` 加 `get_xxx()`，或在组装函数里取 `manager.client` | `get_redis_client()`（仿 `get_embedding_client()` 模式） |
| 6. 业务消费 | service / node 层经注入使用，不直接 import manager | （P2-7 缓存逻辑：`QueryService` 接收 `redis_client` 参数） |

### client manager 模板

```python
"""
XXX 客户端管理器

统一创建和管理 XXX 客户端
主要用于 <业务用途>
"""

from typing import Optional

from xxx_sdk import Client

from app.conf.app_config import XXXConfig, app_config


class XXXClientManager:
    """管理 XXX 客户端的初始化与关闭"""

    def __init__(self, xxx_config: XXXConfig):
        # 保存配置对象，后面初始化客户端时要从这里读取连接参数
        self.xxx_config = xxx_config
        # 先把 client 声明出来，真正初始化放到 init() 中进行
        self.client: Optional[Client] = None

    def init(self):
        """
        显式初始化 XXX 客户端
        这里不在 __init__ 中直接初始化，是为了和项目的生命周期管理保持一致
        """
        self.client = Client(host=self.xxx_config.host, port=self.xxx_config.port)

    async def close(self):
        """关闭 XXX 客户端连接"""
        await self.client.aclose()


# 创建一个全局的管理器对象
xxx_client_manager = XXXClientManager(app_config.xxx)
```

## 三、三类差异点（骨架不变，细节按中间件类型变）

### 1. 配置字段多少

照实定义 dataclass：Redis 只要 `host/port`；MySQL 还要 `user/password/database`。
字段名与 `app_config.yaml` 的 key 严格对应（OmegaConf 按 dataclass 做结构化校验）。

### 2. init / close 的形态

| 类型 | init 产物 | close 方式 |
| --- | --- | --- |
| 简单客户端（Redis / Qdrant / ES / Embedding） | 单个 client 对象 | `await client.aclose()` 或 SDK 提供的关闭方法 |
| 带连接池的数据库（MySQL） | **engine + session_factory**，不是单个 client | 关 engine：`await engine.dispose()` |
| HTTP 型依赖（如 rerank 的 TEI） | `httpx.AsyncClient` | `await client.aclose()` |

SDK 怎么定义就怎么接，不要自行包装出第二套语义。

### 3. 生命周期粒度（最容易踩的差异）

| 粒度 | 适用 | 项目内范例 |
| --- | --- | --- |
| **应用级单例** | 无状态客户端：连接本身可以跨请求复用 | `redis/qdrant/es/embedding_client_manager`：启动建一次，全局复用，关闭释放 |
| **请求级会话** | 有事务/会话语义的数据库 Session | `mysql_client_manager`：`get_meta_session` 里每请求 `async with session_factory()` 开、请求结束关 |

**铁律**：Session 类的对象绝不做单例（事务状态会跨请求串）；无状态客户端绝不每请求新建（浪费连接、拖慢请求）。

## 四、宿主机端口冲突的处理惯例

本项目多次遇到宿主机端口被其他程序/其他项目容器占用，统一处理方式：

1. compose 里映射到备用端口，**加注释写明被谁占用**：`- "6380:6379"  # 宿主机 6379 被 dovideo-ai 占用`
2. `app_config.yaml` 里配置**宿主机映射后的端口**（应用连的是宿主机端口），同样注释
3. 历史案例：MySQL `3307:3306`、ES `9201:9200`、Redis `6380:6379`

## 五、完成后的验证清单

每步做完按此验证，全部通过才算接入完成：

```bash
# 1. 容器连通（基础设施类）
docker compose -f docker/docker-compose.yaml up -d <服务名>
docker exec <容器名> <自带的健康检查命令>     # 如 redis-cli PING → PONG

# 2. 配置加载（确认 yaml 与 dataclass 对得上）
uv run python -m app.conf.app_config

# 3. 客户端真实读写（单事件循环内跑，注意不要多次 asyncio.run）
uv run python <临时验证脚本>                  # set/get 或等价的连通性操作，跑完删除脚本

# 4. 代码检查 + 回归
uv run ruff check <本次改动的文件>
uv run pytest tests -q
```

### 已知坑

- **Windows 下不要在脚本里多次调用 `asyncio.run()`**：每次调用创建并关闭事件循环，异步客户端的连接池跨循环会报
  `RuntimeError: Event loop is closed`。把所有 await 收进一个 `async def main()` 再 `asyncio.run(main())`。
- **`initdb.d` 只在数据卷首次初始化时执行**（MySQL 类服务加初始化 SQL 时）：已有数据卷的环境需 `docker exec` 手动补执行。
- **改了 compose 后容器不生效**：`up -d <服务名>` 会自动重建配置变化的容器；若之前是 `docker run` 起的同名容器，先 `docker rm -f` 再 up。

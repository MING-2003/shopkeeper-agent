# 电商问数（shopkeeper-agent）改进方向分析

> 定位：本文档是对当前项目的一次系统性"体检报告 + 演进路线图"。
> 分析方法：以"这个系统要走向真实生产环境"为标尺，逐层审查现状，推演未来可能出现的问题，再给出改进方案与优先级。

---

## 一、总体逻辑链条

一个智能问数系统从"跑通了"到"能上生产"，必须依次回答五个问题，这五个问题构成本文档的分析主线：

```
第 1 问：生成的 SQL 对不对？          → 正确性层
第 2 问：生成的 SQL 危不危险？        → 安全性层
第 3 问：系统撑不撑得住？             → 性能与成本层
第 4 问：用户好不好用？               → 产品体验层
第 5 问：出了问题能不能查、能不能持续迭代？ → 工程可持续层
```

**核心论断**：当前项目已经跑通了一条完整、可演示的单轮问数闭环（关键词抽取 → 三路召回 → 合并过滤 → SQL 生成 → EXPLAIN 校验 → 修正 → 执行 → SSE 流式返回），这在"教学项目"的标准下是优秀的。但以生产标准衡量，五个层次上都存在系统性缺失，且这些缺失之间存在因果依赖关系——**没有度量就无法优化，正确性没保障时谈性能没有意义，安全是所有功能的前置条件**。

**改进总原则**：
1. **先度量，后优化**——任何改进都应先建评测基准，否则无法证明"改好了"；
2. **硬约束优先于软约束**——依赖 Prompt 的约束都是软约束，必须有程序性防护兜底；
3. **一次只推进一层**——正确性 → 安全 → 体验 → 性能 → 工程化，逐层闭环。

---

## 二、现状与不足分析

### 2.1 正确性层：SQL "对不对" 没有闭环保障

#### 不足 1：SQL 修正只有一次机会，且无重试上限控制

**现状**：校验失败后进入 `correct_sql`，修正后直接执行，没有"再校验、再修正"的循环。

```python
# app/agent/graph.py
graph_builder.add_conditional_edges(
    source="validate_sql",
    path=lambda state: "run_sql" if state["error"] is None else "correct_sql",
)
graph_builder.add_edge("correct_sql", "run_sql")   # 修正后直接执行，不再校验
graph_builder.add_edge("run_sql", END)
```

**未来可能出现的问题**：复杂查询（多表 JOIN、窗口函数、复杂聚合）首次生成的错误率显著高于简单查询，一次修正不够时整条链路直接失败，用户看到报错。同时，反过来若简单粗暴加循环而无上限，失败 case 会无限重试，token 成本失控。

**为什么要改**：修正闭环的正确形态是"校验失败 → 修正 → 再校验"，且必须带最大重试次数（如 2 次）和失败兜底（返回友好提示而非裸报错）。这是 SQL 生成系统的标准做法，也直接决定端到端成功率。

**怎么做**：`DataAgentState` 增加 `retry_count` 字段；条件边改为三分支——校验通过执行 / 失败未超限修正 / 超限走兜底节点。

#### 不足 2：EXPLAIN 校验只覆盖"语法与引用"，不覆盖"业务正确"

**现状**：校验的唯一手段是把 SQL 交给数据库 `EXPLAIN` 一次（`app/repositories/mysql/dw/dw_mysql_repository.py` 的 `validate`）。

**EXPLAIN 能发现**：语法错误、表/字段不存在。
**EXPLAIN 不能发现**：
- JOIN 条件写错导致笛卡尔积（语法正确、结果爆炸）；
- 聚合口径错误（该 SUM 的地方 AVG、指标口径偏离元数据定义）；
- 时间范围错误（"上个月"生成错了日期区间）；
- 结果语义与问题语义不符（用户问销售额，返回了订单量）。

**未来可能出现的问题**：这是问数系统**最隐蔽、最危险**的失败模式——SQL 执行成功，前端展示一个漂亮但错误的数字。用户拿错误数据做业务决策，且没有报错可供排查。

**为什么要改**：语法正确 ≠ 语义正确。生产环境需要三层递进校验：语法校验（已有）→ 静态语义校验（sqlglot 解析 AST，检查 JOIN 条件、聚合字段与元数据口径一致性）→ 结果合理性校验（行数/数值范围异常检测）。前两层程序化，第三层可结合 LLM 自查。

**怎么做**：短期先用评测集（见不足 3）把这类错误量化暴露出来；中期引入 `sqlglot` 做静态检查；长期在 `run_sql` 后增加结果异常检测节点。

#### 不足 3：没有任何评测体系，一切效果都是"感觉"

**现状**：召回质量、SQL 准确率、端到端延迟、修正成功率，全部没有数字。README 的"能力边界"中也承认缺少"系统化评测集与自动化回归评测"。

**未来可能出现的问题**：
- 换模型、改 Prompt、调召回 top-K 参数后，无法回答"变好了还是变坏了"；
- 做了修复循环、rerank 等改进，无法证明改进有效；
- 每次改动都可能悄悄引入回归，且无人察觉。

**为什么要改**：**评测是所有其他改进的前提**。没有度量，"优化"就只是主观感受；有了评测集，每一项改进都能量化验证，整个项目的迭代才能形成"发现 → 改造 → 验证"的科学闭环。

**怎么做**：
1. 构建 50~100 条评测集（YAML）：`问题 → 期望命中的表/字段/指标 → 期望 SQL 或期望结果`，覆盖简单聚合、多条件过滤、多表 JOIN、模糊表述、无答案等 case 类型；
2. 写批量评测脚本，产出四类指标：
   - **召回质量**：表/字段/指标的 Recall@K、命中率；
   - **SQL 质量**：执行准确率（execution accuracy，结果集比对）、语法错误率；
   - **闭环能力**：修正成功率（修正后从失败变成功的比例）；
   - **性能**：端到端 P50/P95 延迟、各节点耗时、token 消耗。

#### 不足 4：召回只有"粗排"，没有精排

**现状**：Qdrant 向量召回和 ES 全文召回的 top-K 结果直接进入上下文构建，中间无 rerank。

**未来可能出现的问题**：当表和字段规模增长（教学数仓十几个字段无感，真实数仓成百上千个字段），粗排候选的噪声占比上升——无关字段挤占上下文窗口，轻则浪费 token，重则把 LLM 的注意力引向错误字段，SQL 生成质量下降。

**为什么要改**："召回 + 精排"是现代 RAG 的标准分工：粗排负责高召回率（宁滥勿缺），精排负责高精度（去噪排序）。字段名/指标描述与用户问法之间存在语义鸿沟（如用户说"GMV"，元数据里叫"支付金额"），cross-encoder 类 reranker（如 `BAAI/bge-reranker-v2-m3`）对这种细粒度相关性判断显著优于向量余弦相似度。

**怎么做**：在三路召回与合并节点之间插入 rerank 步骤，用评测集对比接入前后的 Recall/Precision 变化。

### 2.2 安全性层：LLM 生成的 SQL 正在"裸奔"

#### 不足 5：生成的 SQL 无任何防护直接执行

**现状**：`run_sql` 节点把 LLM 生成的 SQL 直接交给仓储层执行（`dw_mysql_repository.run`），中间没有语句类型检查、没有 LIMIT 限制、没有超时控制；唯一的安全措施是 Prompt 里"只生成 SELECT"的指令。

**未来可能出现的问题**（每一条都是真实生产事故的常见形态）：
- 模型幻觉生成 `UPDATE/DELETE/DROP`——Prompt 是软约束，采样温度、注入攻击、上下文污染都可能击穿它；
- 生成了无 WHERE 条件的 `SELECT *`，全表扫描拉爆内存和连接；
- 慢查询长时间占用连接池，拖垮整个服务；
- 多语句注入（`SELECT 1; DELETE FROM ...`）。

**为什么要改**：安全性必须由**程序性硬约束**保障，而不能依赖提示词。这是"LLM 应用能否上生产"的分水岭问题，也是面试中被追问概率最高的话题之一。

**怎么做**（四道防线，由内到外）：
1. **语句白名单**：用 `sqlglot` 解析 SQL 为 AST，仅放行单条 `SELECT`，拒绝 DML/DDL/多语句；
2. **强制 LIMIT**：AST 检测无 LIMIT 则自动追加（如上限 1000 行），超过上限截断；
3. **只读账号**：数仓连接使用仅 `GRANT SELECT` 的数据库账号，即使前两道防线失效也无法写库；
4. **执行超时**：SQL 级别设置超时（如 30s），超时即终止并降级返回。

#### 不足 6：仓储层存在字符串拼接 SQL 的坏实践

**现状**：`get_column_types` / `get_column_values` 使用 f-string 拼接表名和字段名。

**未来可能出现的问题**：当前输入来自内部元数据文件，风险可控；但一旦元数据来源变成自动同步的外部输入（见不足 12），表名/字段名未经校验就拼接执行，会成为注入面。

**为什么要改**：即使当前风险低，"参数化/白名单校验标识符"也应是数据访问层的默认规范，避免埋雷。

**怎么做**：对标识符做正则白名单校验（`^[a-zA-Z_][a-zA-Z0-9_]*$`）即可消除注入面；对照 information_schema 确认存在性是可选增强（正则通过但对象不存在时数据库会自然报错，不构成注入风险）。

### 2.3 性能与成本层：延迟高、资源利用率低

#### 不足 7：ES 取值召回逐关键词串行查询

**现状**：`recall_value` 节点对每个关键词串行 `await` 一次 ES 查询。

```python
# app/agent/nodes/recall_value.py
for keyword in keywords:
    current_value_infos = await value_es_repository.search(keyword)  # 串行
```

**未来可能出现的问题**：关键词扩展后通常有 5~10 个，每个 20~50ms，串行累加 100~500ms；并发用户数上升时，吞吐被这种串行 IO 直接拖住。

**为什么要改**：这是典型的 IO 密集场景，Python 异步并发是零风险优化；同时 ES 原生支持 `msearch` 批量接口，可进一步把 N 次网络往返压成 1 次。

**怎么做**：`asyncio.gather` 并发所有关键词查询，或改用 ES `msearch`；保持现有去重逻辑不变。

#### 不足 8：无任何缓存，重复问题全链路重跑

**现状**：相同或语义相似的问题，每次都完整走 12 个节点、多次 LLM 调用。

**未来可能出现的问题**：真实业务中问题高度集中（"昨天销售额多少"这类问题每天被问无数遍），全链路重跑意味着 token 成本和延迟双倍浪费；高峰期成本线性膨胀。

**为什么要改**：问数链路中"元数据 → 上下文 → SQL"对于相同问题是完全确定的，天然适合缓存。缓存设计的关键不在"加缓存"，而在**失效策略**——这也是面试考点。

**怎么做**：分层缓存——结果层（相同问题直接返回）、SQL 层（相似问题命中后直接执行）、上下文层（schema 上下文按表缓存）。失效触发：元数据/数仓 schema 变更时按表维度清缓存。

#### 不足 9：所有 LLM 节点共用同一模型，延迟与成本结构不合理

**现状**：关键词抽取、扩展、过滤、SQL 生成、修正全部使用同一个 LLM 配置。

**未来可能出现的问题**：一次问数包含 5~7 次 LLM 调用，若全部使用大模型，端到端延迟轻松超过 10 秒，单次成本也高；而其中过滤、抽取类任务对小模型来说绰绰有余。

**为什么要改**：LLM 应用工程化的核心手段之一是**模型分级路由**——简单任务用小而快的模型，复杂生成任务用大模型，在质量、延迟、成本三者间取得平衡。

**怎么做**：为 `extract_keywords` / `extend_keywords_*` / `filter_*` 类节点配置小模型（如 7B 级），`generate_sql` / `correct_sql` 保留大模型；用评测集验证降级后准确率无可感知损失。

### 2.4 产品体验层：单轮、纯表格，价值表达不完整

#### 不足 10：无多轮对话能力

**现状**：`DataAgentState` 只有一单条 `query` 字段，无任何会话历史。

**未来可能出现的问题**：真实分析场景几乎全是多轮的——"华北销售额多少？"→"那华东呢？"→"按月拆分看看"。当前架构下第二句"那华东呢"无法解析，产品价值被单轮硬性截断；用户只能每次重新完整描述问题。

**为什么要改**：多轮是问数产品从"演示"到"可用"的关键跃迁，涉及两个技术点：会话状态持久化（LangGraph checkpointer + `thread_id`）和指代消解改写（新节点把不完整追问改写为自包含问题后再进入主链路）。这也是深入掌握 LangGraph（checkpointing、time-travel、interrupt）的最佳切入场景。

**怎么做**：
1. 引入 LangGraph checkpointer（`AsyncSqliteSaver` 起步，生产换 Redis/Postgres）；
2. 图入口增加"查询改写"节点：结合最近 N 轮对话，将当前输入改写为独立完整的问题；
3. 改写后的 query 进入既有链路，其余节点无需改动（这是该架构分层清晰的优点）。

#### 不足 11：结果只有原始表格，缺少"最后一公里"的价值表达

**现状**：`run_sql` 执行后把行字典列表直接推给前端。

**未来可能出现的问题**：业务用户要的是"结论"而不是"数据"——面对一张 50 行的表格，非技术用户依然得自己算环比、找异常。系统能力的最后一公里没有被兑现。

**为什么要改**：两个低成本高感知的增强——
- **洞察摘要**：LLM 基于查询结果生成 1~3 句自然语言结论（含环比、异常点提示）；
- **自动图表**：根据结果形状（时间序列 → 折线，分类占比 → 饼图，排名 → 柱状图）推荐并渲染图表。

**怎么做**：新增 `summarize_result` 节点（流式输出摘要），图表推荐用规则引擎即可（不必上 LLM），SSE 协议扩展一种 `chart` 消息类型。

### 2.5 工程可持续层：一次性脚本架构，无法长期运维

#### 不足 12：元数据知识库只有一次性构建，无增量同步

**现状**：元数据构建是一个手动执行的一次性脚本（`build_meta_knowledge`），把 schema 写入 MySQL、向量写入 Qdrant、取值写入 ES，之后三者的新鲜度完全依赖人工。

**未来可能出现的问题**：数仓 schema 是会演进的——字段改名、新增表、枚举值变化。一旦发生，向量库/全文索引与真实 schema 出现**静默不一致**：召回返回已废弃的字段 → SQL 引用错误字段 → 执行报错或更糟（数据错误）。且这种错误极难定位，因为每个环节单独看都"正常"。

**为什么要改**：**元数据一致性是这套"检索增强生成 SQL"架构的命脉**。整套系统的正确性建立在一个假设上——"检索到的元数据是真实 schema 的准确投影"。这个假设失效时，没有任何下游机制能兜底。

**怎么做**：
1. 定时任务对比 information_schema 与元数据库，检测 diff；
2. diff 驱动增量更新：变更字段 → 重新 embedding 并 upsert Qdrant → 重建对应 ES 索引文档 → 清理相关缓存（与不足 8 联动）；
3. 保留 schema 版本号，便于问题追溯。

#### 不足 13：可观测性停留在"日志"层面，无 LLM 调用级追踪

**现状**：已有 `loguru` + `ContextVar` 注入 request_id，能串联一次请求的日志；但 LLM 调用的输入、输出、token 消耗、各节点耗时没有结构化记录。

**未来可能出现的问题**：线上出现"回答质量突然下降"时，无法回答关键问题——是召回变差了？上下文被污染了？还是模型行为漂移了？没有 trace 数据，排障退化为猜测；token 成本构成也说不清。

**为什么要改**：LLM 应用的排障和优化都依赖"每一跳看到了什么"的完整快照。trace 数据同时也是评测集的素材来源——线上坏 case 可以直接沉淀为评测 case，与不足 3 形成闭环。

**怎么做**：接入 Langfuse（可私有化部署）或 LangSmith，在 LLM 客户端封装层埋点，记录每次调用的 prompt、completion、token、耗时、request_id；与 LangGraph 的节点进度流对接，形成"链路视图"。

#### 不足 14：SSE 通道缺乏可靠性设计

**现状**：SSE 只实现了单向推送 progress/result/error，无事件编号、无断线续传、无心跳。

**未来可能出现的问题**：弱网或长查询场景下连接断开，前端要么丢失全部过程信息、要么重复发起完整请求（重复消耗 LLM token）。

**为什么要改**：流式协议在生产环境的可用性取决于断线恢复能力。SSE 原生支持 `Last-Event-ID` 重连语义，改造成本低。

**怎么做**：事件附带自增 `id`，服务端暂存进行中请求的事件流（Redis），前端重连时按 `Last-Event-ID` 补发；配合心跳注释帧（`: ping`）防止代理超时断连。

## 三、未来场景推演：这些不足何时爆发

把上面的不足放到三个演进场景里，可以看清它们的紧迫性排序：

| 场景 | 触发条件 | 首先暴露的不足 |
| --- | --- | --- |
| **从演示到真实用户**（几个业务同事开始日常使用） | 多轮追问、重复提问、期望结论而非表格 | 10（无多轮）、11（纯表格）、8（无缓存）、7（串行查询） |
| **接入真实数仓**（表/字段规模 ×10，schema 持续演进） | 上百字段、定期变更 | 4（无精排）、12（无增量同步）、2（业务正确性）、3（无法度量） |
| **面对生产环境的安全与合规审查** | DBA / 安全团队介入 | 5（SQL 裸奔）、6（拼接 SQL）、14（可靠性） |

结论：**正确性（1/2/3/4）是所有场景的共同地基，安全（5/6）是不可协商的底线，其余按场景紧迫度排期。**

## 四、改进优先级与执行路径

### 优先级矩阵

### 执行路径（形成验证闭环）

```
第 1 步  建评测集（P0-3）
         → 产出：基线数字（召回 Recall@K、SQL 执行准确率、P50/P95 延迟）
         → 顺便暴露当前失败 case 的分布，为后续改进提供靶子

第 2 步  正确性 + 安全加固（P0-1 / P0-5 / P1-6）
         → 产出：修正循环带来的执行准确率提升幅度（用评测集对比）
         → 产出：可演示的安全防护（拦截一条恶意/失误 SQL 的录屏）

第 3 步  深化一项差异化能力（P1-4 rerank 或 P1-10 多轮，二选一做深）
         → 产出：rerank 前后召回指标对比，或可演示的多轮追问流程

第 4 步  性能与工程化（P2 按需）
         → 每项改动跑一次评测集回归，确认无质量退化
```

### 衡量指标定义（评测集产出物）

| 指标 | 定义 | 衡量什么 |
| --- | --- | --- |
| Recall@K（表/字段/指标） | 期望实体出现在召回 top-K 中的比例 | 检索层质量 |
| 执行准确率 | 生成的 SQL 执行结果与期望结果一致的评测集比例 | 端到端正确性 |
| 修正成功率 | 首次失败、经修正循环后成功的比例 | 闭环自救能力 |
| P50 / P95 延迟 | 端到端耗时分布 | 性能与体验 |
| Token 消耗/次 | 单次问数总 token | 成本 |

## 五、一页总结

**现状**：一条完整的单轮问数闭环已经跑通，教学标准下优秀；生产标准下五个层次均有缺失。

**逻辑主线**：
```
能用（已达成）→ 可信（正确性：评测集 + 修正循环 + 业务校验）
            → 可靠（安全：SQL 四道防线）
            → 好用（体验：多轮 + 摘要/图表）
            → 可运营（工程：缓存 + 同步 + 追踪）
```

**第一行动**：先建评测集拿到基线数字——之后每一项改进，都是"数字变好了"而不是"我觉得变好了"。
